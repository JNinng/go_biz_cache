# ADR-0002: 批次全量失效采用世代号递增（key 内嵌 v{gen}）

- 状态：已接受
- 日期：2026-11-17

## 背景

库需提供"批次全量失效"能力（如按定义整体刷新一类缓存），要求"一改全生效"。Redis 下全量失效一个定义的所有 key 有两种基本方案：

1. **SCAN + DEL**：扫描匹配前缀的 key 逐个删除。
2. **世代号（generation）**：物理 key 内嵌 `v{gen}` 段；失效时对元 key `{ns}:{name}:__gen` 执行 `INCR`，此后新构建的 key 落在新世代，旧世代 key 靠 TTL 自然过期。

方案 1 的问题：

- SCAN 成本 O(keyspace)，集群下需逐 master 节点执行，大库时失效耗时分钟级并持续冲击线上延迟；
- 删除窗口与并发写存在竞态（删后写回旧值），需二次扫描兜底；
- 跨实例 L1 清理需广播海量 key，事件载荷不可行。

方案 2 的代价：旧世代 key 占用内存直至 TTL 过期。

## 决策

采用世代号递增：

- 物理 key 统一格式 `{ns}:{name}:v{gen}:{业务键}`，世代号由库管理；
- 世代号存储于 Redis 元 key `{ns}:{name}:__gen`（不占用业务 key 命名空间）；`InvalidateAll` 对元 key `INCR`（原子，避免多实例并发失效覆盖），并发布 `GenerationBumped` 事件；
- 读取端进程内缓存当前世代号，首次 GET 后摊销为 0 次额外 RTT；收到 `GenerationBumped` 事件即时更新；
- 兜底：事件 at-most-once 可能丢失，本地世代号带短 TTL（默认 5s）惰性刷新；窗口内最多读到旧世代旧值（stale 窗口秒级）；
- Redis 不可用时沿用最后已知世代号，不阻塞读取；
- 旧世代 key 靠 TTL 过期；如需提前回收，后续可叠加低频后台增量清理（按旧世代前缀分批 SCAN+DEL，仅加速回收、不影响正确性）。

## 备选方案

- **SCAN + DEL**：如背景所述，成本、竞态、事件载荷三方面均不可接受。被否决。

## 后果

- 失效为 O(1)（单 INCR + 事件），集群友好，无删除竞态（新写入天然进新世代）。
- 旧世代 key 在 TTL 内占用内存（可接受；需要时以后台清理加速回收）。
- 事件丢失时存在秒级 stale 窗口，与 L1 一致性"最终、秒级"的定位一致。
